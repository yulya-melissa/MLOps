Обоснование Архитектуры Границы Системы и Надежности Конвейера

В данном документе приводятся ключевые архитектурные решения, обеспечивающие стабильность, предсказуемость и надежность сервиса детекции огня и дыма при высоких нагрузках и сбоях инфраструктуры.

1. Архитектурные Решения

1.1. Граница Системы: Load Shedding vs Backpressure

Проблема: Внешний веб-клиент отправляет HTTP-запросы через синхронный REST API. В условиях всплеска трафика или остановки воркеров очередь задач заполняется до предельного уровня (FIRE_QUEUE_MAX_LENGTH).

Решение (Load Shedding): При превышении лимита емкости очереди или таймауте публикации API сразу отклоняет входящий запрос с ответом 503 Service Unavailable и заголовком Retry-After: <seconds>.

Почему не Backpressure: Синхронный HTTP-клиент находится вне нашего контура управления. Пауза ответа (Backpressure через задержку HTTP-соединения) приводит к исчерпанию соединений/потоков на клиенте и веб-сервере (HTTP 504 Gateway Timeout / Connection Reset). Мгновенный сброс нагрузки (Load Shedding) защищает серверные ресурсы и явно сообщает клиенту интервал до следующей попытки.

Гарантия согласованности (Пункт 4.2): Порядок операций строго определен как «Publish в RabbitMQ → Insert в Postgres». Если брокер переполнен или недоступен, запрос завершается на этапе публикации: временный загруженный файл сразу удаляется, а запись в БД со статусом PENDING даже не создается. В системе не остаются «висячие» задачи.

1.2. Подтверждение Сообщений (Ack Policy)

Решение: Используется явная ручная политика подтверждений AckPolicy.MANUAL.

Порядок:

Сообщение извлекается из RabbitMQ.

Выполняется upsert в БД со статусом PROCESSING.

Выполняется ML-инференс.

Результат записывается в БД со статусом DONE.

Только после этого вызывается await message.ack().

Почему не AckPolicy.AUTO: Автоматическое подтверждение отправляется сразу при получении сообщения. Если воркер аварийно завершит работу (OOM, сбой питания) во время выполнения ML-инференса, сообщение будет безвозвратно утеряно. Ручное подтверждение гарантирует семантику доставки At-Least-Once (как минимум однократно).

1.3. Идемпотентность и Повторная Доставка

Проблема: Из-за гарантии At-Least-Once одно и то же сообщение может быть доставлено воркеру повторно (например, воркер выполнил инференс и записал результат в БД, но упал до отправки ack).

Решение:

task_id является уникальным первичным ключом (PRIMARY KEY) в таблице tasks.

Все операции изменения статуса используют INSERT ... ON CONFLICT DO UPDATE (upsert) или UPDATE ... WHERE status <> 'DONE'.

Если повторное сообщение приходит на обработку для задачи, которая уже находится в статусе DONE, обновление игнорируется, и повторный ML-инференс не выполняет лишней работы.

1.4. Стратегия Обработки Ошибок и Dead Letter Queue (DLQ)

Ретраи (Retries): При возникновении временных сбоев (например, сетевой сбой при загрузке тяжелых ресурсов) воркер отклоняет сообщение с возвратом в очередь: message.reject(requeue=True).

Счётчик попыток: Число доставок отслеживается через заголовок RabbitMQ Quorum Queues (x-delivery-count).

DLQ: Если число попыток превышает FIRE_WORKER_MAX_ATTEMPTS (по умолчанию 3), сообщение отклоняется без возврата в очередь (message.reject(requeue=False)). Брокер автоматически перенаправляет его в Dead Letter Exchange/Queue (fire.tasks.dlq), а в базе данных статус задачи меняется на FAILED с сохранением текста ошибки.

1.5. Корректное Завершение (Graceful Shutdown)

Проблема: Прерывание воркера во время инференса приводит к незавершенным транзакциям и таймаутам.

Решение:

Воркер отслеживает активные задачи через реестр _inflight (asyncio.Task).

При получении сигнала SIGTERM воркер прекращает принимать новые сообщения из очереди (prefetch_count).

Воркер ожидает завершения всех текущих in-flight задач в течение интервала FIRE_WORKER_SHUTDOWN_TIMEOUT_S (30 с).

Контейнер Docker сконфигурирован с stop_grace_period: 60s, что превышает внутренний таймаут приложения и предотвращает жесткое убийство через SIGKILL.

2. Ответы на Теоретические Вопросы Защиты

Вопрос 5. В чем разница между Load Shedding и Backpressure? Когда что применять?

Load Shedding (Сброс нагрузки): Активное и мгновенное отклонение части входящих запросов (например, с кодом HTTP 503) при достижении предельной утилизации системы.

Применение: На границе системы с внешними необязательными или неуправляемыми клиентами (мобильные приложения, веб-браузеры), где важнее сохранить работоспособность системы для запущенных процессов, чем заставить всех ждать.

Backpressure (Обратное давление): Механизм, при котором медленный получатель замедляет скорость источника данных (например, закон TCP Flow Control или регулирование prefetch_count в AMQP).

Применение: Внутренние асинхронные конвейеры (межсервисное взаимодействие, воркеры очереди), где компоненты контролируются одной системой и могут приостановить чтение без риска обрыва соединений по таймауту.

Вопрос 6. Почему удержания ресурсов в состоянии перегрузки — это плохо? К каким последствиям это приводит?

Накопление каскадных сбоев (Cascading Failures): Когда система удерживает соединения при перегрузке, возрастает использование RAM (буферы, контексты запросов), CPU и пулов соединений с БД.

Исчерпание пула потоков/соединений: Новые запросы блокируются в ожидании свободных потоков серверного веб-каркаса (например, Uvicorn / Gunicorn worker), делая недоступными даже легкие эндпоинты (например, /healthz).

Таймауты клиентов: Клиенты все равно отключаются по таймауту (HTTP 504), но сервер продолжает тратить ресурсы на обработку уже «заброшенных» запросов (Resource Waste).

Вопрос 7. Зачем нужны DLQ и идемпотентность в очереди?

Dead Letter Queue (DLQ): Специальная очередь для "ядовитых" сообщений (Poison Pills) — сообщений с поврежденным форматом или выданных задачей, которая стабильно вызывает падение сервиса. Без DLQ такое сообщение бесконечно циркулировало бы в основной очереди (Infinite Retry Loop), забивая воркеры и блокируя валидные задачи.

Идемпотентность: Свойство системы выдавать одинаковый конечный результат при однократном или многократном выполнении одной и той же операции. В брокерах сообщений из-за сетевых сбоев гарантируется уровень доставки At-Least-Once. Без идемпотентности повторная доставка сообщения вызовет дублирование записей в базе данных или повторное списание средств/выполнение тяжелых вычислений.

Вопрос 10. Как правильно завершать воркеры (Graceful Shutdown)?

Для правильного завершения воркера без потери данных необходимо реализовать следующий алгоритм:

Перехват сигналов: Перехватить системный сигнал завершения (SIGTERM или SIGINT).

Остановка приема (Pause Consuming): Прекратить выборку (fetch/consume) новых сообщений из брокера (установить prefetch_count = 0 / отписаться от очереди).

Ожидание In-Flight задач: Дать текущим асинхронным/многопоточным задачам завершить выполнение и зафиксировать результаты в БД (с отправкой ack).

Таймаут безопасности: Задать жесткий лимит ожидания (Shutdown Timeout). По истечении таймаута принудительно отменить оставшиеся задачи и сделать reject(requeue=True), чтобы их подхватили другие воркеры.

Освобождение ресурсов: Закрыть пулы соединений с БД, соединения с брокером и выгрузить тяжелые ML-модели из памяти.

Настройка оркестратора: Указать в docker-compose.yml / Kubernetes параметр stop_grace_period (например, 60 секунд), превышающий внутренний таймаут воркера, чтобы контейнер не был убит по SIGKILL раньше времени.
